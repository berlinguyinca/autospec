# Cross-cutting invariants

Home for invariants that bind **more than one component** or that outlive the
single file in which they are implemented. A comment in the implementing file
reaches only that file's readers; an entry here reaches the next component.

Rules (see [`runbooks/repository-retirement.md`](runbooks/repository-retirement.md)):

- Every entry states the invariant, **names the components it binds**, and
  links to where it is implemented and where it was decided.
- A new component bound by an existing invariant is added to that invariant's
  components-bound list in the same PR that introduces the component.
- When a component is retired, its invariants are migrated here (or to the
  successor's copy) *before* archival, with the successor added to the list.

| A patch-conversion branch is built hermetically from a pinned base sha — a staged or dirty index is asserted clean before any branch switch, the branch checks out onto the base sha (never a moving ref) before anything is reset, the branch's file list is asserted against the patch's declared file list before push, gate evidence is bound to the commit sha it ran against (publishing refuses when the branch tip moved), and zero commits ahead of the base is a builder error naming the patch, never a silent pass. | `autospec-core` `patch_pipeline` module (`BranchBuild`, `assert_clean_checkout`, `assert_branch_matches_patch`, `require_commit`, `GateEvidence`), the patch→PR conversion caller executing the plan | `crates/autospec-core/src/execution/patch_pipeline.rs` | issue #3915 |

| A system in motion is never read as a system at rest: long-running steps emit a heartbeat and a terminal completion marker; status is a verdict from markers and two samples taken with a gap (never from log recency alone, and `stalled` is unreachable from a single observation); destructive actions (stop, re-dispatch, archive) require a terminal marker or two independent observations; yield/throughput characterisations are computed counts over the whole log, not estimates from the visible tail; and every report keeps the observation (samples, sizes, timestamps) separate from the inference (the verdict). | long-running pipeline passes writing append-only logs, status tooling that reports running / complete / stalled, destructive stop / re-dispatch / archive paths | `scripts/lib/autospec-log-status.sh`, `tests/autospec-log-status.bats`, `docs/runbooks/log-status-observation.md` | issue #3973 |
| A verdict is only worth the base it was measured against: work is finalised against the fetched trunk tip (fetch, rebase, re-run the gates), every emit names its base sha (an emit that names none is a defect, never a missing fact to default), a clean apply onto a moved trunk is staleness and not a conflict, and a `HELD` recorded against a trunk that has since moved N commits is a hypothesis due for re-test, not a decision to re-cite. | `autospec-core` `rebaseline` module, `autospec-core` `patch_pipeline` module (conversion candidates and memos), `autospec-core` `dispatch_guard` module (hold decisions), implementer finalisation path in the `autospec-run` skill | `crates/autospec-core/src/rebaseline/`, `docs/rebaseline.md` | issue #3708 |
| Liveness of a periodic process is read from its own heartbeat line (or its scheduler), never from log-file mtime: every pass appends `heartbeat: <step> <RFC3339Z> [<outcome>]` — including a pass that did nothing — silence past a fixed multiple of the expected interval is `stale` (never "dead"), and a health check first proves it is reading the process's declared log, so a mismatched or absent path is a broken check, not a verdict about the process. | `autospec-core` `heartbeat` module, periodic deployment loops (top-up, auto-scale, reg-sweep) that append to their log, any status tooling that reports a periodic process live / stale / unrecorded | `crates/autospec-core/src/heartbeat.rs`, `crates/autospec-core/tests/heartbeat.rs` | issue #3995 |
