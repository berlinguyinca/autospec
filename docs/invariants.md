# Cross-cutting invariants

Home for invariants that bind **more than one component** or that outlive the
single file in which they are implemented. A comment in the implementing file
reaches only that file's readers; an entry here reaches the next component.

Rules (see [`runbooks/repository-retirement.md`](runbooks/repository-retirement.md)):

- Every entry states the invariant, **names the components it binds**, and
  links to where it is implemented and where it was decided.
- A new component bound by an existing invariant is added to that invariant's
  components-bound list in the same PR that introduces the component.
- When a component is retired, its invariants are migrated here (or to the
  successor's copy) *before* archival, with the successor added to the list.

| Code-intelligence results are cached per `workspace:revision:operation:request` and never reused across worktrees or revisions; degraded (`ast-grep`/`ripgrep`) results are never presented as semantic evidence. | `autospec-core` `code_intel` module, planner / implementer / reviewer gates in `autospec` and `autospec-run` skills | `crates/autospec-core/src/code_intel/`, `.autospec/code-intelligence.yaml` | `AGENTS.md` §"Semantic code intelligence", `docs/code-intelligence.md` |

| A queue artifact is only authoritative while its producer keeps beating: an unstamped or stale queue is a hold (`QUEUE_MISSING` / `QUEUE_UNSTAMPED` / `STAMP_NOT_REFRESHED` / `CLOCK_REWIND`), never "no work"; every hop between filing and dispatch stamps liveness and a silent scheduled hop is a failure. | `autospec-core` `dispatch_pipeline` module, `autospec dispatch` (CLI), `refresh-queue` / `topup` / dispatch-agent deployment hooks, `autospec-run` monitor | `crates/autospec-core/src/dispatch_pipeline.rs`, `crates/autospec-cli/src/commands/dispatch.rs` | issue #3800 |
| A step that holds a credential runs only on a host the operator controls: never on cluster-shared storage, and never as a scheduled step on an `ephemeral-session` host; the topology declares hosts explicitly so the audit names the offending step. | `autospec-core` `dispatch_pipeline` module, `autospec dispatch status` (CLI), deployment cron/systemd units for the refresh and top-up steps | `crates/autospec-core/src/dispatch_pipeline.rs` (`PipelineTopology::audit`) | issue #3800 |
| Destructive remote actions (repo delete/archive, force-push to protected branches, `gh release delete`) are never bypassed: the autonomy gate surfaces a confirmation and gate exit 1 means "ask anyway". | `autospec` skill (Safety guardrails), `autospec-autonomy-gate.sh`, monitor/stop-mode paths | `scripts/autospec-autonomy-gate.sh`, `skills/autospec/SKILL.md` | `AGENTS.md` §"Autonomy charter", `docs/AUTONOMY-CHARTER.md` |
| A staged spec carries the source issue's `updatedAt`, the staging time, the discussion since the last body edit and a probed execution-environment block; a dispatch is held when the staged revision is stale and **refused when freshness cannot be verified at all** — an unreadable live issue is never read as "unchanged". | `autospec-core` `staged_spec` module, `autospec dispatch stage` / `dispatch freshness` (CLI), merge-host staging hooks, cluster dispatch path | `crates/autospec-core/src/staged_spec.rs`, `crates/autospec-cli/src/commands/dispatch_spec.rs` | issue #3864 |
| Restoring a file is not making the restoration visible: every harness that corrupts and restores a tracked file (test fixtures, recovery traps, session restore) must `touch` the restored path in the same scope, including trap paths; every rebuild a test depends on is followed by an artefact-content assertion, because an mtime gate is a producer, not a proof. | all shell/bats harnesses under `scripts/`, `tests/`, `skills/` | `scripts/lint-restore-visibility.sh`, `tests/lint/test_restore_visibility_checker.bats` | issue #3878, `AGENTS.md` §"Restore-visibility contract" |
| A spec document without a currency marker is never read as current. Dispatch refuses a set with no marker (`CURRENCY_MISSING`), refuses a superseded set naming its successor (`SPEC_SUPERSEDED`), and treats a component claimed by two sets in force as a hard error (`AUTHORITY_CONFLICT`) reported to a human: the tool reports and stops, it never chooses which spec program wins. | `autospec-core` `spec_authority` module, `autospec dispatch` (`stage`, `freshness`, `authority`), `autospec-plan` decomposition (spec sets it reads from `docs/specs/`), the `autospec-run` monitor | `crates/autospec-core/src/spec_authority.rs`, `crates/autospec-cli/src/commands/dispatch_authority.rs`, `scripts/validate-spec-authority.sh` | issue #3947 |

A task naming no authority is counted under `undetermined` and warned about rather than dropped: a dropped row is a silently wrong merge count. | `autospec-core` `spec_authority` throughput model, `autospec dispatch authority --tasks`, the `autospec-run` monitor (per-authority reporting) | `crates/autospec-core/src/spec_authority.rs`, `crates/autospec-cli/src/commands/dispatch_authority.rs` | issue #3947 |
