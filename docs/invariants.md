# Cross-cutting invariants

Home for invariants that bind **more than one component** or that outlive the
single file in which they are implemented. A comment in the implementing file
reaches only that file's readers; an entry here reaches the next component.

Rules (see [`runbooks/repository-retirement.md`](runbooks/repository-retirement.md)):

- Every entry states the invariant, **names the components it binds**, and
  links to where it is implemented and where it was decided.
- A new component bound by an existing invariant is added to that invariant's
  components-bound list in the same PR that introduces the component.
- When a component is retired, its invariants are migrated here (or to the
  successor's copy) *before* archival, with the successor added to the list.

| Destructive remote actions (repo delete/archive, force-push to protected branches, `gh release delete`) are never bypassed: the autonomy gate surfaces a confirmation and gate exit 1 means "ask anyway". | `autospec` skill (Safety guardrails), `autospec-autonomy-gate.sh`, monitor/stop-mode paths | `scripts/autospec-autonomy-gate.sh`, `skills/autospec/SKILL.md` | `AGENTS.md` §"Autonomy charter", `docs/AUTONOMY-CHARTER.md` |
| A staged spec carries the source issue's `updatedAt`, the staging time, the discussion since the last body edit and a probed execution-environment block; a dispatch is held when the staged revision is stale and **refused when freshness cannot be verified at all** — an unreadable live issue is never read as "unchanged". | `autospec-core` `staged_spec` module, `autospec dispatch stage` / `dispatch freshness` (CLI), merge-host staging hooks, cluster dispatch path | `crates/autospec-core/src/staged_spec.rs`, `crates/autospec-cli/src/commands/dispatch_spec.rs` | issue #3864 |
| A patch is graded by the same gate set its staged spec names: a gate run with a weaker or stronger command than the spec names is `unenforced` (never counted clean), a gate never run is named in the verdict instead of counted as clean, and a spec that names no gates grades nothing — a run graded against a weaker set is not a run the spec asked for. | `autospec-core` `grading` module, `autospec-core` `staged_spec` module, `autospec dispatch stage` (CLI), fleet grading status line (`autospec-fleet`) | `crates/autospec-core/src/grading.rs`, `crates/autospec-core/src/staged_spec.rs`, `crates/autospec-cli/src/commands/dispatch_spec.rs` | issue #3925 |
| Restoring a file is not making the restoration visible: every harness that corrupts and restores a tracked file (test fixtures, recovery traps, session restore) must `touch` the restored path in the same scope, including trap paths; every rebuild a test depends on is followed by an artefact-content assertion, because an mtime gate is a producer, not a proof. | all shell/bats harnesses under `scripts/`, `tests/`, `skills/` | `scripts/lint-restore-visibility.sh`, `tests/lint/test_restore_visibility_checker.bats` | issue #3878, `AGENTS.md` §"Restore-visibility contract" |
| A patch-conversion branch is built hermetically from a pinned base sha — a staged or dirty index is asserted clean before any branch switch, the branch checks out onto the base sha (never a moving ref) before anything is reset, the branch's file list is asserted against the patch's declared file list before push, gate evidence is bound to the commit sha it ran against (publishing refuses when the branch tip moved), and zero commits ahead of the base is a builder error naming the patch, never a silent pass. | `autospec-core` `patch_pipeline` module (`BranchBuild`, `assert_clean_checkout`, `assert_branch_matches_patch`, `require_commit`, `GateEvidence`), the patch→PR conversion caller executing the plan | `crates/autospec-core/src/execution/patch_pipeline.rs` | issue #3915 |
| A queue entry's produced patch is a mid-lifecycle state, never a terminal one: entries carry state (`queued` / `produced` / `converted`) in a consumer-owned ledger with monotonic stamps, a hold preserves the state and records its reason, a released produced entry re-enters the next tick as a conversion (not a fresh dispatch), produced-but-unconverted is directly queryable, and a tick that dispatches nothing names every skip with its reason. | `autospec-core` `dispatch_pipeline` module (`LifecycleLedger`, `EntryState`, `DispatchTick`), `autospec dispatch tick` / `dispatch mark` (CLI), dispatch-agent deployment hooks | `crates/autospec-core/src/dispatch_pipeline.rs`, `crates/autospec-cli/src/commands/dispatch.rs` | issue #3911 |
| Worker selection is one shared implementation, never reimplemented inline by a dispatcher: stateless (it reads the server's live slot state and Slurm time-left, and nothing else), load-aware (it ranks by real free slots and filters on context sufficiency, not maximum context), total over answering workers (a saturated fleet still names the least-loaded worker), with refusal as a separate admission decision (zero-free-slot workers are held, not dispatched). A dispatcher that picks several workers in one pass passes its prior picks to the picker so a pass never stacks on one worker before live state has caught up. | `dispatch-gw.sh`, `topup.sh`, `iw-dispatch.sh` (deployment dispatchers over the shared worker pool) | `<llm>/select-worker.sh` (dot-sourced by all three), `<llm>/test-select-worker.sh` (offline test harness) | issue #3929, issue #3714, issue #3733, issue #3754 |
| Every committed generated artefact names its generator and every committed consumer in a `# Consumers(<path>): …` block in the generator script; recorded digests of the artefact and the existence of every enumerated consumer are re-verified on every run, so regenerating an artefact can never silently break a consumer that the generator does not know about. | `scripts/gen-harness-runtime-aliases.sh`, `config/harness-runtime-aliases.tsv`, `templates/generated/harness-runtime-aliases.{sh,fish}`, `docs/generated/harness-runtime-aliases.md`, `config/generated-artifact-integrity.sha256`, `install.sh` | `scripts/lint-generated-artifacts.sh`, `tests/lint/test_generated_artifact_integrity_checker.bats`, `autospec validate::check_generated_artifact_integrity` | issue #3893, `AGENTS.md` §"Generated-artifact consumer contract" |
| A system in motion is never read as a system at rest: long-running steps emit a heartbeat and a terminal completion marker; status is a verdict from markers and two samples taken with a gap (never from log recency alone, and `stalled` is unreachable from a single observation); destructive actions (stop, re-dispatch, archive) require a terminal marker or two independent observations; yield/throughput characterisations are computed counts over the whole log, not estimates from the visible tail; and every report keeps the observation (samples, sizes, timestamps) separate from the inference (the verdict). | long-running pipeline passes writing append-only logs, status tooling that reports running / complete / stalled, destructive stop / re-dispatch / archive paths | `scripts/lib/autospec-log-status.sh`, `tests/autospec-log-status.bats`, `docs/runbooks/log-status-observation.md` | issue #3973 |
| Liveness of a periodic process is read from its own heartbeat line (or its scheduler), never from log-file mtime: every pass appends `heartbeat: <step> <RFC3339Z> [<outcome>]` — including a pass that did nothing — silence past a fixed multiple of the expected interval is `stale` (never "dead"), and a health check first proves it is reading the process's declared log, so a mismatched or absent path is a broken check, not a verdict about the process. | `autospec-core` `heartbeat` module, periodic deployment loops (top-up, auto-scale, reg-sweep) that append to their log, any status tooling that reports a periodic process live / stale / unrecorded | `crates/autospec-core/src/heartbeat.rs`, `crates/autospec-core/tests/heartbeat.rs` | issue #3995 |
