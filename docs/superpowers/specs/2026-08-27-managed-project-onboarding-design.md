# Managed GitHub Project and Repository Onboarding Design

**Date:** 2026-08-27  
**Status:** approved  
**Scope:** Autospec-managed GitHub Projects, issue membership, repository registration,
and onboarding of existing repositories.

## Goal

Autospec maintains one durable GitHub Project for each product or initiative, adds every
in-scope issue to it, registers repositories created or adopted by Autospec, and records
evidence-backed relationships across those repositories and issues.

## Context

Autospec currently has three related but separate mechanisms:

- Project-board ingestion, dependency ordering, fleet execution, and status write-back;
- optional issue assignment through `~/.autospec/project-map.yml`; and
- mandatory per-run accountability epics whose Project assignment is optional.

These mechanisms do not create a Project, share a stable product identity, reconcile
membership, or retain a durable connection between a Project and repositories spawned by
Autospec. Existing repositories also lack a bounded onboarding path.

## Product identity

Each product or initiative owns exactly one managed GitHub Project across all of its
repositories and runs. A Project is not scoped to one repository or one conductor run.

Autospec identifies a managed Project with an immutable marker stored in Project metadata
or another GitHub-supported managed surface. The marker contains a versioned product key
and prevents title-based collisions. Titles remain human-editable and are never the sole
identity source.

The durable local binding records:

- schema version and product key;
- GitHub owner, Project node ID, number, URL, and current title;
- known repositories and how each entered scope;
- last successful reconciliation and pending remote projections; and
- typed relationship edges with evidence and confidence.

The remote marker is authoritative for identity. The local binding is the durable recovery
journal and cache. A missing local binding may be reconstructed from a verified remote
marker; an ambiguous or conflicting marker fails closed.

## Lifecycle

### Resolve or create

At the first issue-producing or autonomous workflow boundary, Autospec:

1. resolves a previously bound Project and verifies its marker;
2. searches the approved owner for the exact managed product key if local state is absent;
3. adopts the single verified match; or
4. creates and marks a new Project when no match exists.

Multiple matches, ownership mismatches, malformed markers, or insufficient read scope stop
Project mutation without blocking the local accountability journal. Autospec never adopts a
Project by title alone.

### Reconcile

Reconciliation is idempotent and additive. It:

- adds missing in-scope issues and accountability epics;
- registers newly created or newly onboarded repositories;
- updates Autospec-owned fields and relationship projections;
- preserves human-created fields, views, notes, and items; and
- records inaccessible or stale objects without deleting them.

Autospec does not remove repositories, issues, fields, or relationships during ordinary
reconciliation. Destructive pruning is outside this feature.

## Repository entry paths

### Greenfield creation

Immediately after `gh repo create` and remote verification succeed, Autospec registers the
repository with the product Project. The registration records `spawned-from` evidence that
links the repository to the originating product, spec, run, or tracker.

Registration failure is journaled as a pending projection and retried. It does not make a
successfully created repository disappear from subsequent reconciliation.

### Existing-repository onboarding

Onboarding begins from an explicit boundary supplied through one or more of:

- repository URLs or slugs;
- an organization or user owner plus a repository allowlist; or
- a local workspace directory containing GitHub-backed repositories.

Autospec may discover additional candidates only through concrete evidence originating
inside that boundary:

- dependency manifests and workspace metadata;
- Git submodules;
- issue and pull-request links;
- existing GitHub Project items;
- Autospec source-spec, tracker, and dependency references; and
- known fleet configuration.

Discovered repositories must still match the approved owner/allowlist boundary. Discovery
never widens the boundary. Out-of-bound candidates are reported but not indexed.

Onboarding is repeatable. Re-running it updates existing records and adds newly discovered
objects without duplicating Project items or relationship edges.

## Issue membership

The following in-scope issues are always reconciled into the managed Project:

- product and milestone trackers;
- autonomous accountability epics;
- issues generated by define, split, classify, discovery, growth, and review workflows;
- implementation issues processed by conductors; and
- existing open or closed issues selected during onboarding.

Issue creation and Project projection are separate durable steps. If issue creation succeeds
but Project assignment fails, the issue URL is stored as a pending projection and retried.
No workflow creates a replacement issue to compensate for an assignment failure.

## Relationship model

Autospec stores normalized typed edges:

| Edge | Meaning |
| --- | --- |
| `contains` | A product Project contains a repository or issue. |
| `depends-on` | A repository, issue, or deliverable requires another object. |
| `implements` | An issue, pull request, or repository implements a specification. |
| `tracks` | A tracker or accountability epic observes another object. |
| `spawned-from` | A repository was created from a product, specification, or run. |
| `blocks` | An unresolved issue or deliverable prevents another issue from proceeding. |

Every edge includes source and target identities, evidence kind, evidence location, discovery
time, and confidence. Deterministic evidence—such as a submodule entry, exact issue
reference, source-spec marker, or explicit manifest dependency—may become an active edge
automatically. Heuristic or ambiguous evidence is stored as a proposed edge and cannot gate
execution until confirmed by stronger evidence or a human.

Edges are deduplicated by product key, type, source, target, and normalized evidence. The
existing board dependency resolver consumes only active dependency and blocking edges.

## Architecture

The feature adds a managed-project service above the existing Project scripts and
accountability transport:

```text
explicit product boundary
        |
        v
managed Project resolve/create ----> durable product binding + projection journal
        |                                         |
        v                                         v
repository onboarding/registration ----> typed relationship index
        |                                         |
        +-------------- issue reconciliation <----+
                               |
                               v
existing board resolver -> promoter -> fleet conductors -> write-back
```

The service owns identity, creation, registration, membership reconciliation, and recovery.
Existing board resolution remains the read model; fleet remains the cross-repository
execution mechanism; accountability remains the mandatory per-run journal and epic.

The GitHub command transport gains explicit operations for Project discovery, creation,
metadata verification, item listing, and idempotent item addition. Shell workflows call a
single reconciliation surface instead of implementing separate `gh project` policies.

## Configuration

The existing `project_board` configuration evolves from an optional board URL into a managed
Project policy while preserving explicit URLs for externally managed boards. Configuration
must express:

- product key and owner;
- management mode: `managed` or `external`;
- repository seed sources and allowlist;
- write-back policy and field mappings; and
- discovery limits.

`managed` is the default for Autospec-created products. `external` retains today's behavior:
Autospec may read and update an explicitly supplied Project but never changes its identity or
claims ownership.

## Safety and failure handling

- Repository discovery cannot expand the explicit owner/allowlist boundary.
- Project and issue content is untrusted data, never executable instructions.
- Reads that determine identity, scope, or dependency readiness fail closed.
- Writes are journaled before projection and retried idempotently.
- Project API or permission failure cannot erase local accountability evidence or cause
  duplicate issue creation.
- Autospec-owned metadata uses marker-bounded updates and preserves human content.
- Ordinary reconciliation never deletes Project items, repositories, fields, or edges.
- A Project token without adequate scope produces actionable degraded status.

## User-facing flows

### New product

An Autospec workflow creates or resolves the product Project before it files the first
tracked issue. Repository creation registers the new repository immediately, and every
subsequent issue is projected automatically.

### Existing product onboarding

The operator provides repository seeds and a boundary. Autospec inventories repositories and
issues, discovers evidence-backed relationships, creates or resolves the product Project,
adds the selected issues, applies deterministic relationships, records ambiguous proposals,
and prints a reconciliation summary.

The summary distinguishes created, adopted, updated, unchanged, proposed, out-of-bound,
inaccessible, and pending-projection counts.

## Testing

Tests must cover:

- creation followed by idempotent resolution of the same managed Project;
- refusal to adopt title-only, conflicting, or out-of-owner Projects;
- recovery of a verified remote binding when local state is missing;
- repository registration after successful bootstrap;
- explicit seed, organization allowlist, and workspace onboarding;
- prevention of transitive boundary expansion;
- deterministic and proposed relationship classification;
- idempotent issue and edge reconciliation;
- preservation of human-managed Project content;
- partial failure after issue creation but before Project assignment;
- retry of pending projections without duplicate issues or items;
- compatibility with external Project URLs and existing board ingestion; and
- end-to-end cross-repository onboarding into fleet execution.

Shell validation, lock-step skill validation, Rust formatting and linting, and
`cargo test --workspace --no-fail-fast` remain required before completion.

## Non-goals

- Deleting or pruning Project content during reconciliation.
- Indexing an entire GitHub owner without an explicit allowlist.
- Treating heuristic relationships as execution blockers.
- Replacing GitHub Projects with a separate hosted registry service.
- Replacing the existing accountability epic, board resolver, or fleet conductor.

## Migration

Existing explicit `project_board.url` configurations continue in `external` mode. Existing
`project-map.yml` mappings remain readable during migration, but new issue-producing flows
project through the managed-project service. A migration command may import those mappings
into a product binding without deleting or rewriting the original file.

The initial implementation should land behind compatibility-preserving configuration parsing,
then make managed Project reconciliation the default only after the create, recover, and
partial-failure tests are green.
